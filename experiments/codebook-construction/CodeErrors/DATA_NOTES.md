# 材料核查与补充编码

## 393：补充编码为 C08「条件判断错误」

该多项式求根实现采用二分法。算法选择本身不是错误；实际缺陷是忽略左端点已为根的情况。当系数为 `[100,1]` 时，多项式为 `100+x`，左端点 `a=-100` 已是唯一根。进入二分后，`poly(xs,a)*poly(xs,c)<0` 在左端值为零时不成立，程序执行 `a=c`，丢掉已有根。

原码实际返回 `99.99999925494194`，发布数据的参考代码返回 `-100.0`，官方 HumanEval 参考返回约 `-100.00000000005821`。这个输入满足偶数项系数和最高次系数非零的条件。原码还未通过官方 HumanEval/32 的完整 check；该结果另外保留，不把其所有失败都解释为端点问题。

已有 C08 定义涵盖比较严格性、分支条件与 guard 错误，因此加入 C08。C17 的边界明确将普通比较等号错误交给 C08；同一端点缺陷不重复赋予 C17，也不新增只适用于二分求根的类别。

## 729：补充编码为 C14「排序或选择优先级错误」

题目同时写了“按长度升序，同长按字母排序”和“可以假定所有词等长”，确有文字冲突。仅看后一句不足以确定不同长度输入的预期。此次取回 HumanEval 官方原数据与测试，确认官方测试明确包含不同长度单词，发布数据的参考实现和官方参考实现也都采用长度优先规则。因此按这个有可执行证据支持的操作契约完成编码，仍记录题目文字冲突。

官方已有断言：

```python
assert candidate(['aaaa', 'bbbb', 'dd', 'cc']) == ['cc', 'dd', 'aaaa', 'bbbb']
```

生成代码过滤奇数长度字符串后调用默认 `sorted(...)`，只比较字母顺序，实际返回 `['aaaa','bbbb','cc','dd']`。原码通过官方 7 条断言中的 6 条，在上述断言失败；发布数据参考和官方参考都通过全部 7 条。错误机制是缺少主长度排序键，符合 C14；过滤本身正确，不额外赋予步骤遗漏类别，不为该案例新建类别。

原始 HumanEval 文件下载自官方 `openai/human-eval` 仓库；所取两个任务原记录、测试、来源地址和文件 SHA-256 保存在 `shared/humaneval-evidence/`。官方测试表明基准的实际要求，但不声称它们就是 Code errors 原研究当时实际执行的同一份测试。

## 编码范围

- “缺少导入/依赖”基于材料提供的完整代码片段，不自动注入 math、re、hashlib 或 helper。若原运行环境预载这些依赖，需按该环境重新评估这些标签。
- 对无实现、截断或重复展开，描述的是交付代码的状态，不推断生成中断、token 上限或模型动机。
- 不把合法的不同算法、未测量的性能差异或规格以外输入视为确定错误。
- 保留的编码本包括交付完整性、可执行性及行为语义。对“语义根因”作严格统计时，应区分实现缺失/依赖/API 类与已能解释行为差异的类别，不能将它们全部解释为模型内部推理原因。
- 第一轮案例 142 中关于 `')'` 的循环不前进观察被排除为正式标签，因为任务规定输入是平衡括号组；有效输入 `'()'` 返回空列表已经足够支撑目标/范围错误。这是有效输入域审计，不是忽略已发现的代码。
