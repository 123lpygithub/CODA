# SATD 与 Privacy：原论文、公开数据与当前证据缺口核查

核查日期：2026-11-05。本文基于两篇原论文全文、Zenodo 复制包、GitHub 当前复制仓库、上游采集/处理脚本和 CODA v6 缺口清单。Code errors 不在本次核查范围。

## 1. 核心结论

目前并不是两个数据集都缺少“发布的样本”。SATD 的 856 条最终注释记录、Privacy 的 652 条确认相关 issue 记录均已取得。缺少的主要是**样本背后的完整历史证据**：注释的唯一代码位置、当时的完整讨论、已删除的 issue，以及关联的旧文件和外部材料。

也不能将剩余问题全部归因于网络或数据删除。核查发现，当前实现还有明确的扩展空间：SATD 应利用上游中间文件确定其他历史版本，再验证版本关系；Privacy 应处理 issue 转移、PR 页面、包含斜杠的分支名，并按分析需要扩展 GitHub 之外的上下文。

原研究“公开了可重算结果的数据”不等于“公开了所有人工阅读材料的不可变快照”。尤其 Privacy 的分析 notebook 可以用人工编码列重新计算统计图，完全不需要重新读取 issue 正文。这种复现与重新执行一次无标签的质性编码不同。

## 3. ML SATD 原研究是怎样获取数据的

### 3.1 原始材料和筛选

原论文 §2.1 说明，研究从既有 ML 项目集合中选择 Python 项目，使用截至 **2021 年 1 月**的源码历史。候选 Python 项目有 2,684 个，其中 43 个在生成数据时已不在 GitHub，最终分析 2,641 个项目。README 指明 Boa 数据集名称为 `2021 Jan/ML-Verse`。

作者没有先从 GitHub 找到 856 条注释，再逐条抓取页面。他们使用 Boa 对历史版本中的注释变更做批量查询，然后筛选和抽样：

1. 提取 9,725,127 条注释变更。
2. 去掉长度不足的内容后，保留 7,415,024 条。
3. 取 SATD 分类器与关键词检索结果的并集，剩余 193,787 条变更。
4. 去除自动生成等无关内容，剩余 189,912 条。
5. 关联注释的引入/删除事件，得到 85,599 条唯一注释。
6. 去除 `site-packages` 中的非项目原生内容，最终候选池为 68,820 条。
7. 分层按比例抽取 856 条进行人工分类。

论文 Table 2 的最终样本组成与 CODA 本地 CSV 完全对应：

| 样本分层 | 数量 |
| --- | ---: |
| Tool，注释已删除 | 101 |
| Tool，注释未删除 | 245 |
| Application，注释已删除 | 127 |
| Application，注释未删除 | 383 |
| 总计 | 856 |

### 3.2 人工编码和上下文

原研究结合已有 taxonomy 与开放编码，形成传统软件 SATD、ML SATD 和 ML pipeline stage 等标签。§2.3 说明先以 100 条注释做 pilot；§2.4 说明两名作者独立标注、第三名作者主持讨论，最终每条注释至少由两名作者检查。它不是在完全不提供已有类别的条件下开展的纯归纳实验。

不能说原研究完全不看代码。§5 的 Construct validity 明确说明，作者检查过 SATD 周围的代码，排除一些注释已不再相关的案例。但公开最终表并未把这些代码片段、行号和每次人工检查证据一并保存下来。

### 3.3 公开文件实际保存什么

最终 `sampled_label_dataset.csv` 有：数据集 ID、项目类型、仓库名、文件路径、注释引入提交、注释删除提交、注释文本和人工分类列。它没有完整源码、唯一行号或完整仓库快照。

本次读取了 `get_comment_changes.boa`。关键输出语句为：

```text
commentData << p.name + "," + revId + "," + fileName + "," + txt + "," + chng;
```

这证明最初导出的查询结果只有仓库、提交、路径、文本和变更类型，没有导出源码位置或 AST 节点身份。脚本还主动将逗号替换为分号，把换行替换成 ` || `。因此，公开注释文本不是完全未经处理的源码字节。

Zenodo 的 `1-output.txt` 约 1.57 GB、`2-id_output.txt` 约 1.67 GB；文件大不代表其中包含全量源码。脚本说明明确指出后者只是为相同记录增加数据集 ID。要从 Boa 恢复唯一位置，需要查询底层数据并修改导出字段，不能仅靠下载大文件保证解决。

本次实际下载并检查了较小且足够定位问题的 `13-apps.csv`、`13-tools.csv`、约 38 MB 的 `9-link_output.txt`，以及 Boa/Python 脚本和标注过程工作簿。**7 条剩余记录都在 `9-link_output.txt` 中找到，仍被记为 ADDED；这些中间行没有新增行号。**

下述三个候选与发布提交的关系，并以 `historical_partial` 接入：Catalyst 使用
已验证祖先版本，Paysage 使用具有共同祖先的相关分支，Lightning 使用后续版本。
856 条现在均有代码片段；4 条位置歧义和 3 条版本差异仍然存在。具体快照与运行
前核对见 [当前实验指南](PAPER_EXPERIMENT_RUN_GUIDE.md)，不能把相关版本补充称为
原始案例指定版本的完整源码。

当前 849 条有可唯一匹配的上下文。其中 5 条来自已验证的直接父提交，并在 agent 输入中明确标注版本差异；所以不能把 849 全部称为“在发布的引入提交中唯一匹配”。

剩余 4 条在指定版本中存在多个相同注释位置。程序已保留全部候选片段，不足之处是无法知道原抽样记录指向哪一个位置。标注工作簿中的直接文件链接也没有行锚点：检查到 1,232 个超链接，`#L` 定位链接为 0。这属于公开记录缺少定位信息，并非下载失败。

### 3.5 还发现哪些复制包问题

- 本地最终 CSV 与 GitHub 仓库当前最终 CSV 解析后的 856 条记录相同，没有漏下载。
- Zenodo CSV 与 GitHub CSV 只有一个实质文本行差异：Zenodo 物理第 814 行在 Comment Text 前多了一个双引号。默认 CSV 解析会吞并后续多行，只读出 825 条。当前 CODA 使用的 GitHub 文件已经修正这行，能读出 856 条，不能简单替换成 Zenodo 文件。
- 最终 856 行只有 853 个不同的 Dataset ID，3 个 ID 各出现两次。当前用行号加原 ID 构造 artifact ID 的方式有必要。
- `labeling_process` 的第四轮 agreement 工作簿与最终 CSV 的 ID 集没有交集；按仓库、路径、提交和规范化完整文本匹配，只有 310 条最终记录能对应。可以确认这些文件不能按 ID 直接连接，但不能据此断言作者标注有误，也不能用工作簿直接覆盖最终表。

## 4. Privacy 原研究是怎样获取数据的

### 4.1 项目范围与采集时间

正式论文 §3.1（PDF 第 7–8 页）规定：分析 2016 年 4 月至 2022 年 12 月的英文 GitHub issue；项目公开、非 fork、有许可证；2018 年 6 月后至少 10 名贡献者、100 次提交、20 条 issue。

作者在 **2023-01-23 至 2023-01-31** 使用 GitHub Search API，以 GDPR、personal data、cookie banner、right to be forgotten 等关键词检索。检索结果经过人工验证，移除非隐私相关项，再继续随机补抽，得到 652 条确认相关 issue。

因此，`coded_issue_data.csv` 的 1,761 行不是 1,761 条最终隐私案例。本次实际统计为：652 条 `true`、1,108 条 `false`、1 条 `xxx`。CODA 选择 652 条 `true` 与发布的最终相关样本规模对应。

### 4.2 人工实际阅读什么

§3.3（PDF 第 9 页）说明：通过 GitHub API 自动取得报告者、标签、评论数、参与人数、报告日期、最后活跃日期、状态；以下五个变量由人工编码：

- Trigger：为什么提出问题；
- Privacy issue：隐私问题类型；
- Consent interaction：涉及的同意交互；
- Resolution：处理结果；
- Reason for resolution：处理原因。

§3.1 还明确允许读取项目提交、邮件列表、Jira 等外部 issue tracker、项目政策等附加材料。§5.6.1（PDF 第 37 页）强调编码者看的是 whole issue，而不是只看对应类别的片段。

原文没有充分说明正文和全部评论是否以原始 API 响应形式永久保存，也没有在公开复制包提供这样的快照。可以确认作者需要阅读讨论来编码；不能由此进一步声称所有讨论原文都已公开。

### 4.3 人工编码过程和材料固有的模糊性

两位作者共同独立编码约 20% 的材料并多轮讨论，之后又各增加两轮 5% 的共同编码。论文报告平均 IRR 最后为 0.44，并明确解释：一些讨论对外部人员很难理解，只有内部开发者能正确解读。后续主要由一人继续编码，遇到不确定内容仍讨论；另由一位此前未参与编码的作者核查约 10% 材料。

这不意味着原数据不可用，但说明**即便拿到全部评论，也不保证所有解释都能确定**。对 CODA 而言，“证据已下载完整”与“处理结果有充分依据”必须分别判断。

### 4.4 复制包实际包含什么

固定 Zenodo v1.0 包含 `all_issues.csv`、`coded_issue_data.csv`、`label_merge.csv`、`participants.csv`、`analysis.ipynb`、图表和依赖。当前 GitHub 主分支另有 `additional_analysis.ipynb`、`coded_issue_data_verification.xlsx`。

本次实际检查了完整 ZIP、CSV 列名、notebook 源码和额外工作簿：

- CSV 保存标题、URL、项目、日期、评论数量、参与者、状态、标签及人工分类等。
- 没有 issue body 列、逐条 comment body、完整 JSON 讨论快照，也没有批量下载原始讨论的采集脚本。
- `participants.csv` 只有 `index, project, login, commits, reports`，不能补出讨论正文。
- 额外 verification 工作簿记录二次人工核验结论，不能作为缺失原始正文使用。
- 两个 notebook 主要读取 CSV 并计算编码分布、相关关系和模型。它们能重算论文分析，不能从隐藏的正文存档恢复历史讨论。
- 当前 GitHub 与固定复制包中的 `all_issues.csv`、`coded_issue_data.csv`、`label_merge.csv` 字节一致；未发现更新仓库已补齐正文。

### 4.5 原研究自己就遇到过资料消失

正式论文 Fig. 8（PDF 第 19 页）明确写道：

> There are three issues, which were deleted from GitHub when we checked for the reason marked as “–”.

复制包中对应三条记录的 `reason_rater_2` 为 `ISSUE HAS GONE`：

| 发布记录 | issue |
| --- | --- |
| `privacy-issue-11387` | `MicrosoftDocs/microsoft-365-docs#2560` |
| `privacy-issue-2476` | `taigaio/taiga-front#1462` |
| `privacy-issue-17517` | `wappalyzer/wappalyzer#1482` |

这三条也在当前历史证据案例中。此处查看人工列仅用于核查原研究是否也曾遇到删除；这些人工结论没有用来重建正文，也没有加入 agent 输入。

原文还报告有些 issue 虽已关闭，仍无法确定解决方式。因此，以 closed 状态补写“已修复”不符合原研究的实际情况。

### 4.6 原文与复制包的总量也不完全一致

正式论文 §3.1 说检索到 21,608 条、5,892 个项目；§4.1 则报告满足条件的 12,606 条、5,069 个项目。本次下载的 `all_issues.csv` 实际为 **12,660 条、5,069 个项目**，notebook 保存的输出同样是 12,660。

前两组数字可能涉及不同筛选范围，但正文没有清晰交代。12,606 与 12,660 是否为排版错误或版本差异，无法仅由公开材料确定。它不改变最终 652 个相关案例的对应关系，却说明不能把原文所有候选池数字当成完全一致的采集清单。

## 5. 当前采集还需要改进什么

### 5.1 SATD：转为有目标的版本核验

优先利用本次找到的同仓库、同路径、完整同文的上游记录。核验 Git 父子/祖先关系及修改过程，保存真实源码、提交、校验和与“不同版本”说明。确认后可作为补充上下文；仍无法对应的记录保留原文，不伪装成指定引入版本。

对于 4 条重复注释，继续使用全部候选片段。如果 Boa 原始数据可访问，可以查询注释对应的 AST/source position；但须先确认旧数据集仍可访问、其位置字段能与当初 ADDED 记录对应。重复注释的唯一归属不会因为普通重试自动出现。

### 5.2 Privacy：先修复访问路径，再扩展上下文范围

当前 652 条都已取得正文证据，635 条有完整当前讨论，16 条只有历史正文/评论，另有 1 条当前评论数不一致。关联记录有 430 条可用、17 条部分可用、95 条不可用。95 条包括 78 个文件与 17 个 issue。

不能把 95 条都称为永久不可恢复。目前还有具体实现问题需要解决：

1. **含斜杠的分支名。** 如 `/blob/next/v99/...`。现采集器按单一路径段切分 ref，可能把 `next/v99` 拆成 ref=`next` 与错误文件路径，导致本可读取的材料被记为 404。应通过仓库 ref/页面元数据确定分支与路径边界。
2. **issue 到 PR 的跳转。** `/issues/821` 可能对应 PR 或跳转到 PR 页面，当前只解析 `issueViewerRoute` 会报错。应识别最终资源类型，再分别取 PR 正文、普通评论、review comments、patch 和状态。
3. **仓库迁移和 issue 转移。** 应验证 GitHub 的规范 URL、迁移关系与具体 issue 身份，不能仅因号码改变就接受或拒绝。`vector-im/riot-web#2458` 是待核实实例。
4. **外部材料。** 原论文允许读取 Jira、邮件列表和项目政策；当前补采仅支持 GitHub 显式链接，覆盖范围更窄。对恢复的主讨论做链接盘点，共发现 1,939 次非 github.com/raw.githubusercontent.com URL 引用、1,641 个不同 URL，涉及 443 个案例；其中包括截图、Jira、政策、法规、示例和无关网址。这不是“必须再下载 1,641 份”的数量，而是需要按编码解释所需进行筛选的上下文清单。
5. **二进制附件。** 如 `userscripts_v2.7z` 不是 UTF-8 文本，当前文本采集器不能直接解码。应保留明确的附件类型，只有分析确实依赖它时再做受限解包和文件提取。
6. **历史内容与当前内容的边界。** 网页归档/公开事件可提供历史证据，但不能证明覆盖了所有编辑、删除及评论。完整性结论必须限定到所保存的时间与材料范围。

外部链接清单见 `privacy-external-url-inventory.json`。本次盘点只覆盖主正文/评论，不包含单独的历史追加材料，也未证明每个 URL 对研究问题都重要。

### 5.3 什么只能由原作者或额外档案补齐

如果原作者保留了原始 API 响应、爬取数据库或离线讨论副本，这是恢复 2023 年阅读材料的最直接来源。公开 v1.0、当前 GitHub 和 notebook 中未找到这些文件；不能据此断言作者私下没有保存。

如后续需要联系作者，所需材料应具体限定为：652 个最终案例的正文/评论时间快照及采集日期、删除案例的历史副本、转移映射和人工阅读的附加材料清单。SATD 可询问最终行与 Boa 注释事件/位置的映射，以及 3 条提交指针不匹配记录的来源。此处只是列出需要的材料，本次没有发送邮件或消息。

## 6. 对 CODA 当前实验的建议

保留全部发布案例及其编号；对 S1/S2/S3 冻结完全相同的证据输入。将“当前完整”“历史部分”“位置歧义”“无法获取”分别记录，不能让不同审核设置拿到不同版本的证据。

完整讨论不等于所有关联材料完整，材料完整也不等于解释一定正确。证据不足的 assignment 应保持不可评判或待处理，不以原研究的人工分类反推缺失材料。评估时同时报告覆盖情况及不可评判数量。

当前论文中的“comment and its recoverable source-code context”和“linked development artifacts included when available”允许明确记录这些恢复边界。无需为了本次调查改写数据集选择；但若实际运行仍使用历史或部分证据，复制材料和评估记录必须说清楚范围，不能声称重建了原研究全部历史证据。

本次是来源与采集方式调查。未修改论文、人工参考标签、冻结 v6 agent 输入或实验结果；新发现的其他提交代码仅保存在调查目录，尚未替换任何案例上下文。
