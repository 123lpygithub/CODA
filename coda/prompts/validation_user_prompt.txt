Review criteria:
- R1: unresolved coding disagreement that comparison and validation cannot resolve;
  different labels for the same concept or permitted complementary codes do not qualify.
- R2: insufficient or conflicting evidence, missing context, incompatible revisions, or an explicit abstention.
- R3: unresolved category boundary or overlap for the same interpretation; permitted multiple coding is not itself a conflict.
- R4: merge, split, or meaning/inclusion/exclusion change to an established category with accepted assignments.
- R5: conflict with a recorded human decision or an approved category condition.
- R6: explicit refusal directly, or malformed/incomplete output or missing
  case/category/source references that persist after one recorded repair using the same
  evidence. Do not invent a repair record; valid deferrals belong to R2/R3.

Constraints:
- Record unchecked target IDs, missing inputs, and inspection limits in notes. Do not
  claim an omitted original source, prior case, or programmatic check was inspected.
- For initial_codebook/final_audit, report concrete stage findings through signals,
  questions, and notes; do not label them iterative R1-R6 flags or grant stage approval.
- In initial_codebook scope, inspect the provisional categories, inclusion/exclusion
  conditions, original sources, both coders' observations, and initial assignments.
  Identify relevant phenomena lost or distorted by summarization or consolidation,
  unsupported grouping, and unclear boundaries. Return clarification or revision
  findings; never declare the initial codebook human-approved.
- In final_audit scope, validate the recorded assignment against the FINAL codebook
  and full original case. The comparison section is a reconstruction of the recorded
  decision, not a new agent proposal; an empty coder list does not indicate coder failure.
  Check category clarity, meaningful coverage using the corpus counts and this case,
  stale or inactive code references, omitted phenomena, unsupported claims, source
  locations and available revision identifiers. An explicit unresolved or uncoded
  record is not itself malformed. Never overwrite a recorded human judgment.
  This is operational audit, not independent RQ1 scoring or proof of corpus correctness.
- Emit use_case_mismatch when the proposed peer codes answer different analytical
  dimensions from the one requested by the research question.
- Emit category_overlap or boundary_unclear when several codes appear to be different
  locations or repair manifestations of one underlying issue rather than independently
  meaningful coding units.
- Use issue_scope "assignment" when the problem can be corrected by changing only this
  artifact's code_ids, including parent-child co-assignment. Use "codebook" only when the
  category definitions, hierarchy, analytical axis, or boundaries themselves require revision.
- Emit unsupported_inference when an alleged error is justified only by structural
  difference from a reference implementation and no behavioral departure is grounded.
- Confidence is descriptive metadata only. It must never determine human-review routing.
  A locally supported new code may be high; merge, split, refine, rename, and parent-category changes
  require closer scrutiny because they alter existing boundaries.
- For interpretive_ambiguity, "high" means greater ambiguity and "low" means little ambiguity.
- Validate add_parent separately from merge: add_parent must preserve at least two distinct
  child codes and introduce one evidence-grounded parent with independent analytic utility.
  A broad label alone is not evidence for a parent category.
- If the case is mostly sound but still needs human attention, keep both "valid" and "human_review_required" if useful.
- Use only evidence ids that appear in the context packet.
- Every explanatory string must have its paired Chinese field with the same meaning.
- Do not output markdown.
